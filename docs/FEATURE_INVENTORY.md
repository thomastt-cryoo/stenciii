# M0 — Complete source and capability inventory

Audited on 29 October 2026 (Asia/Dubai). Destination repository: [thomastt-cryoo/stenciii](https://github.com/thomastt-cryoo/stenciii). Upstream: [filipealmeida/graffiti-stencil-maker](https://github.com/filipealmeida/graffiti-stencil-maker).

## Source identity and audit boundary

The upstream default branch and latest non-prerelease both resolve to **v2.9.4**, commit **`5d8df15b798b859faf72248a35d156d6e9aaffc7`**. The annotated tag object is `c56971f9ffc80ebdce7478ca100ca637354bc899`; distinguish the tag object from its peeled source commit. Commit time is 28 October 2026 17:54:35 UTC (21:54:35 Dubai). Release published at 18:00:10 UTC; the macOS asset was added at 18:06:03 UTC. The commit is titled “Release v2.9.4: Remove fragments node”; it **adds** the Remove fragments processing type rather than deleting an existing capability. No newer source commit was found at audit time.

Upstream history is retained locally. `upstream` points to the original repository; `origin` points to the user's new repository. The shell lacks GitHub push credentials, so the connected GitHub integration publishes a complete source/audit snapshot with separate remote commit ancestry. The original source commit above remains the provenance pin, and its full history remains available through the local upstream references. M0 adds audit evidence and, only when needed, baseline test/build fixes. The node-based application remains present for baseline comparison; replacing it belongs to the next authorized milestone.

The pinned tree has 107 files. [source-manifest.json](audit/source-manifest.json) lists every path, byte length, line count where applicable, and SHA-256 of the pinned Git bytes. The review covered the four root guides, all four Rust crates, all frontend source and E2E files, build/lock/configuration files, both workflows, both fonts and their license. Generated build artifacts and installed dependencies are evidence, not part of the pinned source tree.

## Verified counts and what they mean

**24 runtime processing types and 217 type-qualified parameter slots**, including the legacy combined exporter, eight intermediate-tone override groups, image asset identity and serialized layout edits. A name such as `bridge_mm` used on several types counts once for each type; this is not 217 unique spellings. `complexity` is a migration alias for `remesh`, not a 25th type. Every catalogue entry has a real execution function. `PARAMETERS.md` is generated by the CLI; the audit compares its per-type names and counts with the executed catalogue, and the upstream CLI test compares the full generated reference.

Exact field types, defaults, limits, numeric increments, choices, groups, ports and descriptions are in the executed [runtime catalogue](audit/runtime-catalogue.json). Each field's new location, conditional semantics and verification method are in [FEATURE_UI_MAPPING.md](FEATURE_UI_MAPPING.md). [parameter-mapping.json](audit/parameter-mapping.json) makes completeness checkable by tools. Mapping coverage is 24/24 types and 217/217 slots; redesign implementation and comprehensive per-value verification are later work.

## CLI and output behavior

The [captured CLI help](audit/cli-help.txt) is the complete user-facing flag reference. The CLI's direct image pipeline is image → threshold → raster/vector stencil → optional legacy export/hardware; its defaults come from graph catalogue fields, not necessarily `Params::default()`. The graph path supports both native execution graphs and ReactFlow-style saved graph objects, embedded image id remapping and `complexity` migration.

Preserve image flags (vector/detail/resolution/threshold/invert), size/material flags, bridge count/spread/angle/passes/length, contact/first-layer/overhang controls, layer/flip flags, tiling/connectors/gap/bevel flags, pads/mounting/hardware options, thread count, project/source override, repeatable validated `--set`, layout PNG, print/report JSON, strict exit, parameter listing/markdown, folder batch and cartesian sweeps. Batch creates one folder per run, report JSON, summary CSV and a best seam-step result; each run uses its own process so one failure does not stop the rest.

Real formats are: original PNG/JPEG/BMP/SVG bytes; working image/mask/layout PNG; traced/cleaned shape SVG; binary STL; individual parts and stored-entry ZIP; version 2 embedded-image JSON projects; presets JSON; readiness JSON/console output; batch summary CSV. There is no G-code, OBJ/3MF, machine slicing, corrected-stencil SVG or text/image compositor in this source. Retain the legacy CLI and all engine encodings even when the old UI does not have a direct button for each one.

CLI export collects unconsumed processing **instances**, not every output independently. Hardware reads upstream mounting metadata but returns only new hardware files. Consequently a terminal hardware step can hide the plate/tile files from the CLI's leaf selection. The replacement ExportPlanner must explicitly include chosen products and auxiliaries rather than copying this assumption. M0 records this behavior; it does not redesign CLI exports.

## Build, release, licensing and risks

The workspace has core, WASM, CLI and launcher crates. CI builds/tests Rust on Ubuntu, builds both WASM modes, patches thread worker JS, performs npm audit/TypeScript/Vite, runs Chromium E2E with threading expected, embeds the app and deploys Pages on main. Release builds Windows x64, macOS arm64 and Linux x64 ZIPs when a `v*` tag is pushed; the threaded build is optional there. There is no Tauri configuration, signed installer, macOS Intel build, PWA, cross-browser test matrix or automated clean-machine offline test. Docs-only paths are omitted from CI triggers.

All three published ZIPs are below 20,000,000 bytes. These are upstream packages, not new Stencil Studio deliverables; new source-build sizes are in the baseline evidence.

The root code uses the Unlicense; bundled DejaVu fonts have their own Bitstream/DejaVu notices. Dependency manifests include MIT/Apache/BSD/Zlib/Unicode licenses and at least one MPL-2.0 dependency; do not describe the entire bundle as solely Unlicensed. [dependency-licenses.json](audit/dependency-licenses.json) records resolved package/version/license declarations for review, including dev/build dependencies (not all are shipped). It is an inventory, not a completed distribution notice bundle. Current release packaging copies only README/INSTALL/USAGE/root LICENSE, omitting the DejaVu notice and consolidated third-party notices; retain source notices now and fix package notices before selling downloads. Modified MPL-covered dependency files would need specific review; no dependency code is modified in M0.

Major conflicts and implementation risks:

- A dedicated contrast operation and builder bridge-off toggle do not exist. Avoid fake controls or quiet algorithm changes; use threshold semantics and bridge status, with any additions separately tested.
- Mask/outline previews differ from corrected 3D material, especially for raised bridges; an SVG must not imply correction it does not contain.
- Tile-first returns parts; remesh/colour registration require solids. Bevels belong to post-solid split. Preserve strategy choices and explain incompatibilities.
- Ten colour masks versus six registered solids; do not discard extra passes. Text does not overlay images.
- Hardware file aggregation, duplicate filenames across branches and CLI leaf export selection can omit or overwrite outputs; use an explicit manifest.
- The CLI advertises `--seam-angle` but its direct image pipeline writes `seam_angle_deg` into the legacy `export` operation, whose catalogue does not define it; evaluation therefore ignores it. The actual bevel capability exists on `tiles` and is reachable through a project override. Preserve it there and track the direct-flag defect separately; do not call this flag tested functional.
- Remove-fragments volume/count data is produced in `meta.fragments`, but the standard readiness finding functions do not render those metrics. The new parts inspector must expose them explicitly, especially when artwork is removed.
- Remesh material preservation is tolerance-bounded, not a strict no-loss guarantee; skip and fallback behavior must be visible.
- Working resolution, supersampling, extra layers and mesh detail can cause heavy memory use; source cache and frontend blob caches have separate retention limits. MT requires headers/shared memory and runtime support; hard worker restart loses caches but must restore assets.
- Worker-pool initialization has no timeout. The Windows helper-path fix addresses the reproduced boot failure, but other subworker failures can still leave initialization pending; add and test a startup watchdog in a later reliability step.
- Existing project/parameter import is permissive, whereas evaluation normalizes values. A replacement serializer must retain unsupported data before normalization and never rebuild arbitrary imports from templates.
- A rapid New → reopen of the same saved graph left computed outputs blank in the local browser check until explicit Rerun. The saved graph and original image bytes survived; run-signature deduplication versus cleared result state needs an explicit import-generation test in the new controller.
- UI/readiness state can outlive geometry generation; prevent stale or coarse results from appearing fully verified on export.
- Independent exported-file validation finds zero-area triangles in the raster ring and connector fit-test strip despite closed edges and engine watertight verdicts. Vector samples pass. Track this as an existing geometry-quality issue; do not hide it behind the 156 passing Rust tests or automatically repair artifacts during the audit.
- Windows/macOS offline runtime availability, unsigned launch friction, missing notices, browser origin-dependent autosaves and 20 MB packaging must be tested on actual deliverables. Tauri is only a candidate; see [UX_ARCHITECTURE.md](UX_ARCHITECTURE.md).

The exact tested baseline and readiness gate are in [BASELINE_TESTS.md](BASELINE_TESTS.md). M0 is complete only after the evidence and audit documents are committed; M1 remains paused pending the user's next instructions.
