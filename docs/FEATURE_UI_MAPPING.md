# M0 — Feature preservation and proposed interface

Audit date: 29 October 2026 (Asia/Dubai). Source: v2.9.4, `5d8df15b798b859faf72248a35d156d6e9aaffc7`. This document specifies future destinations; the existing UI is unchanged in M0.

## Coverage rules

Every runtime `type.parameter` gets a distinct row below, including repeated names, all eight intermediate-tone overrides, hidden image identity, serialized manual layout edits, and the legacy combined exporter. The accompanying [machine-readable matrix](audit/parameter-mapping.json) records original location, type/default/range/step/choices, dependencies, tier, destination and verification. The [runtime snapshot](audit/runtime-catalogue.json) also preserves exact labels, ports and documentation. Full mapping means no feature was omitted from the design; it does **not** mean the replacement UI has been implemented or every possible parameter combination has been tested.

T1 = everyday / quick controls. T2 = commonly useful settings near the top of All Settings. T3 = specialist workflows. T4 = expert manufacturing or compatibility. A specialist operation can contain everyday controls without putting its entire configuration on the main screen. Search indexes operation labels, parameter names, former names, units and dependencies. An inactive setting remains discoverable with an explanation and its saved value.

## Verification and routing contract

The main inspector edits one selected product/colour pass. Global size and fit controls clearly indicate scope; layer-specific changes cannot leak into other passes. Each field routes to the exact qualified parameter, with overrides stored per operation instance. Search results include values that are currently inactive. Reset-to-engine-default and apply-template are different commands, and changing a style on a complex imported recipe offers a new copy instead of discarding its steps.

Every catalogue port remains in the internal model. A runtime result can have only `solid` **or** `parts` available despite both being declared. UI routes by available outputs, rather than assuming that every stencil returns one STL. `hardware` consumes mounting metadata but does not pass input tile files through; export must explicitly collect the plate branch and hardware branch. Remesh accepts `solid`, colour registration accepts `solid`, while tile-first produces `parts`; the product must explain these restrictions and preserve alternate workflows rather than silently reconnecting them.
